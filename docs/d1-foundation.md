# D1 Foundation

D1 databases apply `apps/api/d1-migrations/0001_initial.sql` through `0022_transaction_needs_confirmation.sql`. The first defines the ledger, import, scheduler/receipt, audit, guarded-write, and auth foundation; migrations 0002–0009 add password auth and the reviewed import/planning/scheduling/reconciliation extensions; 0010 enforces unique live import IDs; 0011 stores revocable, user-scoped personal API token fingerprints; 0012 stores synced account-organisation preferences; 0013 splits a leading account icon from the name; 0014 backfills leftover leading name emojis that 0013 skipped (variation selectors and surrounding spaces); 0015 stores Rewards Tracker export snapshots and cards; 0016 adds query indexes for transfer-graph lookups, live register paging, reconciled-date probes, and live payee lists; 0017 materialised the YNAB month activity baseline into `ynab_source_month_activity` for the month view, which has since been removed with budgeting; and 0018 adds `account_month_balances`, a per-account, per-month net-change aggregate that serves the net-worth report, plus `report_cache`, a small knowledge-keyed cache for age of money. Migration 0018 rebuilds the aggregate from history and installs three triggers on `transactions` that recompute the affected account-month after any insert, delete, or balance-changing update, so every write path maintains it without code changes. Any future migration that rebuilds the `transactions` table must recreate those triggers. Migration 0019 copies imported YNAB schedules into HowMuch's own schedule tables and records the "came from YNAB" plan marker in `plans.ynab_sourced`, so the raw mirror is provenance only. Migration 0020 drops the three budgeting tables (0005, 0006 and 0017) that nothing reads any more. Migration 0021 adds `card_payment_terms`, one row of statement and due-date terms per card account, with same-plan ownership triggers; it is additive. Migration 0022 adds `transactions.needs_confirmation` (default 0) and a partial index over the marked live rows; it is additive and older Workers ignore the column. Trailing emojis stay on the name. Imported YNAB objects remain read-only. Effective projections combine the source with guarded local changes and are not written back to YNAB. Reconciliation is a post-cutover HowMuch write and must not be followed by a YNAB re-import. This is a focused migration surface, not a claim of full YNAB feature parity.

The account/transfer-payee relationship deliberately uses ordered creation plus ownership triggers rather than immediate cyclic foreign keys. Ledger sequence triggers and unique indexes preserve deterministic ordering. D1 writes remain complete atomic batches with write-version, receipt, assertion, and lease checks.

Wrangler binds the reviewed D1 databases: `howmuch-production-sg` for production (env `tk`) and `howmuch-preview` for preview. The `howmuch-production` databases (the top-level binding in the YJ account, and the KIX copy in the Tinkertanker account) are frozen backups; never migrate or write to them (see `AGENTS.md`). A target starts clean, then the validated offline YNAB bootstrap may load the verified ledger, provenance, and source mirror; never use an ad-hoc database copy.
